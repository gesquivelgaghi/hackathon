# Accessibility testing

This page documents the three layers of automated a11y checks in this repo. Each layer has a different responsibility and a different blast radius for failure.

| Layer                    | Owns                                                                                              | Trigger                                                                  | Gate                                         |
| ------------------------ | ------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------ | -------------------------------------------- |
| `eslint-plugin-jsx-a11y` | Static JSX patterns (missing `alt`, bad `role`, click-without-keyboard, etc.)                     | `lint.yml` on PR                                                         | Blocks PR (existing lint gate)               |
| Lighthouse CI            | Full-page audit at initial DOM of unauth + auth URLs; score-based gates; sticky PR comment        | `pull_request` (annotate), `workflow_dispatch` (block), nightly schedule | Annotate on PR; block when invoked manually  |
| Playwright + axe-core    | Interactive states: modals open, side panels open, toasts visible, validation errors, focus traps | Existing `e2e-tests` matrix on PR                                        | Blocks PR on `serious`/`critical` violations |
| `vitest-axe`             | Component-level a11y regressions before they ship to CI                                           | Existing `unit-tests` job on PR                                          | Blocks PR                                    |

axe-core is the rule engine Lighthouse uses internally for its accessibility category — rule overlap is intentional. The difference is _where in the page lifecycle_ each layer runs and _who owns the gate_.

## Lighthouse CI

### What we check

The Lighthouse **accessibility** category is run against a fixed list of URLs served by the Vite dev server. The audit matrix and the per-level floor are defined in [.github/lighthouse/audit-sets.cjs](../../.github/lighthouse/audit-sets.cjs); each entry carries an inline comment naming the WCAG success criterion it most closely covers. We run Level **AA** by default (floor `0.90`), with a Landscape-specific `heading-order` override pinned to `warn` while the Vanilla Framework heading-structure migration is in flight.

### How CI invokes it

[.github/workflows/lighthouse-a11y.yml](../../.github/workflows/lighthouse-a11y.yml) calls the reusable workflow three ways:

| Trigger | Mode | URL set | Comment | Notes |
| --- | --- | --- | --- | --- |
| `pull_request` to `main` | `annotate` | `urls.public.txt` | Yes — sticky | Never blocks merge during the soak period. |
| `workflow_dispatch` | `block` or `annotate` (caller choice) | `public` / `msw` / `both` (caller choice) | No | Use this to dry-run a stricter gate before flipping the PR job. |
| `schedule` (nightly 03:30 UTC) | `annotate` | `both` | No | Catches regressions on URLs we don't scan on every PR. |

### How to run locally

```bash
pnpm install
pnpm dev                                # terminal A — keeps running on :5173
LHCI_AUTH_MODE=public pnpm a11y:ci      # terminal B — exits 0 if at/above floor
```

No `pnpm build` step: we scan the Vite dev server directly so a single edit-save-rerun loop is enough to iterate on a regression. Override the level or score floor by setting `LHCI_WCAG_LEVEL` (`a` / `aa` / `aaa`) or `LHCI_MIN_SCORE` (`0`..`1`).

### Interpreting a failure

1. Open the PR's `Lighthouse a11y / pr-public` check and read the sticky comment — it lists the failing URL, the score, and the top failing audit IDs with their WCAG mapping.
2. Download the `lighthouse-report-pr` artifact attached to the workflow run and open the HTML report for the specific URL. Each failing audit links to the offending DOM node and a remediation page.
3. Reproduce locally with the commands above, then iterate.

### Tuning

Edits land in [lighthouserc.cjs](../../lighthouserc.cjs):

- **Override an audit** — `config.ci.assert.assertions["audit-id"] = ["warn"]` (or `["error", { minScore: 0.9 }]`). We already ship one such line for `heading-order`.
- **Change the floor** — pass `minScore` to `createBaseConfig` (or set `LHCI_MIN_SCORE` for an ad-hoc run).
- **Add a URL** — append to `publicUrls` (or `authenticatedUrls` for `LHCI_AUTH_MODE=msw`).

Long-lived overrides should carry a brief comment explaining the reason and a planned removal trigger.

## Playwright + axe

This layer runs `@axe-core/playwright` against the same Playwright tests that already drive the `e2e-tests` matrix, but in **interactive states** that static URL audits (Lighthouse CI) cannot reach: modals open, side panels open, success notifications visible, validation error states, focus traps.

The gate is intentionally narrow — only axe violations with `impact === "serious"` or `impact === "critical"` block the PR. Lower-impact issues are still attached to the test report as JSON so engineers can see them, but they don't fail the build.

### When to add a Playwright+axe test

Add a spec under `e2e/features/a11y/` whenever you ship one of:

- a new modal (including all variants — confirmation, form, full-screen)
- a new side panel (Add, Edit, View, or any custom flow)
- a new toast / inline notification surface
- a new focus-trap-bearing surface (any dialog or popover that owns the user's keyboard input)

Component-level a11y for the underlying component lives in [`## Component-level (vitest-axe)`](#component-level-vitest-axe); this layer covers the **state** the user actually sees, after navigation and interaction.

### The `scanA11y` API

Exported from `e2e/support/helpers/a11y.ts`:

```ts
scanA11y(page: Page, testInfo: TestInfo, label: string, options?: {
  include?: string;                  // single CSS selector-list, e.g. ".p-modal, [role='dialog']"
  exclude?: readonly string[];       // one selector per array entry; each adds an axe `.exclude()` call
  tags?: readonly string[];          // WCAG tag override; defaults to wcag2a, wcag2aa, wcag21a, wcag21aa
  disableRules?: readonly string[];  // escape hatch for known upstream bugs; always pair with a TODO
}): Promise<void>
```

The helper:

1. Runs `AxeBuilder` against the page with the configured tags + scope.
2. Attaches the full `AxeResults` as `axe-<label>.json` via `testInfo.attach()` — visible in the Playwright HTML report **and** uploaded as a separate `a11y-report-<matrix-target>` artifact in CI.
3. Filters violations to `serious` and `critical` impact, then asserts the list is empty. The failure message lists each blocking rule with its impact, id, node count, and help text.

Skeleton spec:

```ts
import { test } from "../../support/fixtures/auth";
import { scanA11y } from "../../support/helpers/a11y";

test.describe("@a11y @saas <surface>", () => {
  test("<surface> has no serious/critical a11y violations", async ({
    authenticatedPage,
  }, testInfo) => {
    await authenticatedPage.goto("/<route>");
    // bring the surface into view (click, fill, etc.)
    await scanA11y(authenticatedPage, testInfo, "<label>", {
      include: ".p-modal, [role='dialog']",
    });
  });
});
```

The `@a11y` tag wires the spec into `pnpm test:a11y:saas` or `pnpm test:a11y:self-hosted` (both are `playwright test --grep @a11y`). The `@saas` / `@self-hosted` tag picks the matrix project per `playwright.config.ts`.

### Scoping with `include` / `exclude`

For modal, side-panel, and toast scans, pass `include` so axe doesn't also flag pre-existing violations in the unrelated background DOM. Selector reference:

| Surface                      | `include`                                                           |
| ---------------------------- | ------------------------------------------------------------------- |
| Modal                        | `".p-modal, [role='dialog']"`                                       |
| Side panel                   | `".side-panel"`                                                     |
| Toast / success notification | `".p-notification--positive"` (or the appropriate severity variant) |
| Full page                    | omit `include`                                                      |

Use `exclude` to suppress a single known-issue selector when an upstream component (e.g. a third-party widget) has a violation you can't fix. Each entry in the `exclude` array becomes one axe `.exclude()` call; arrays-as-frame-chains semantics from the underlying API are intentionally not exposed here.

Use `disableRules` when the violation is genuine and rule-wide — i.e. the upstream component has a bug that fires the same rule everywhere it's used, and you can't scope around it with a selector. Always pair `disableRules` with a TODO comment that names the upstream issue, so the deferral is visible in code and survives PR review. See `e2e/features/a11y/login.spec.ts:17–22` for an in-tree example.

### Running locally

The a11y specs run against two environments; each needs its own dev server mode.

```sh
# terminal A — start the dev server
cp .env.local.example .env.local   # if you haven't already
pnpm dev                              # uses default VITE_SELF_HOSTED_ENV from .env.local
```

```sh
# terminal B — SaaS specs (modals, toasts, focus traps, overview, login)
pnpm test:a11y:saas

# terminal B — Self-hosted specs (Repositories side panels)
pnpm test:a11y:self-hosted
```

`pnpm test:a11y:saas` is equivalent to `VITE_SELF_HOSTED_ENV=false VITE_MSW_ENABLED=false pnpm exec playwright test --grep @a11y --project=saas`; it runs against the real backend.

`pnpm test:a11y:self-hosted` sets `VITE_SELF_HOSTED_ENV=true VITE_MSW_ENABLED=true` and targets `--project=self-hosted`. The self-hosted specs (Repositories/Mirrors side panels) depend on the debarchive API, which is only available on a real self-hosted Landscape instance — so these specs run against MSW mock data instead of the live API. Both write `axe-*.json` files under `test-results/`.

After either run, open the HTML report to inspect attachments:

```sh
pnpm test:report   # opens the Playwright HTML report; expand any a11y test to see the axe-*.json attachment
```

To verify the gate is wired correctly, temporarily strip an `aria-label` from an icon-only button in `src/templates/dashboard/Sidebar.tsx`, run `pnpm test:a11y:saas`, and confirm `overview.spec.ts` fails with `[serious] button-name (...)`. Revert the change.

### Reproducing a CI failure

1. Download the `a11y-report-<matrix-target>` artifact from the failed run (one per matrix leg).
2. The archive contains all `axe-<label>.json` files emitted by failing and passing specs. Pick the one named after the failing test's `label`.
3. Each violation in `violations[]` has `id`, `impact`, `help`, and `nodes[].html` — paste a `nodes[].html` into the running app's DevTools to confirm the issue locally.
4. Fix, re-run the appropriate local command (`pnpm test:a11y:saas` or `pnpm test:a11y:self-hosted`), and push.

The `axe-*.json` payloads are also embedded inside the `playwright-report-<matrix-target>` artifact's HTML report — the standalone `a11y-report-*` artifact exists for greppability (e.g. `find . -name 'axe-*.json' | xargs jq '.violations[] | select(.impact == "serious")'` across an unpacked archive).

### Per-project tag note

The `saas` Playwright project uses `grepInvert: /@self-hosted/` and vice versa, so a spec tagged `@a11y @saas` runs **only** in the `saas` matrix leg (silently skipped in `self-hosted`). v1 specs default to `@a11y @saas`; cross-tag with `@self-hosted` when the surface differs between deployment modes (or replace the tag entirely, as the two `sidepanel-*` specs do for the self-hosted-only Repositories area).

## Component-level (`vitest-axe`)

### When to add one

Add a component-level a11y test whenever you ship — or substantially alter — a component that controls focus, hides content from assistive technology, or builds its own DOM scaffolding rather than composing existing primitives. The standing list:

- Modals and confirmation dialogs (`Modal`, `ConfirmationModal`, anything using `role="dialog"`).
- Side panels (`SidePanel`, `SidePanelFormButtons`).
- Navigation / sidebar shells.
- Any new component that renders an `aria-*` attribute or sets `tabindex` directly.

These tests live in [src/tests/a11y/](../../src/tests/a11y/) — one file per component, named `<Component>.a11y.test.tsx`.

### Usage pattern

```tsx
import { axe } from "vitest-axe";
import { renderWithProviders } from "@/tests/render";
import MyDialog from "@/components/.../MyDialog";

it("has no detectable axe violations", async () => {
  const { container } = renderWithProviders(<MyDialog open />);
  expect(await axe(container)).toHaveNoViolations();
});
```

The `toHaveNoViolations` matcher is registered in [src/tests/setup.ts](../../src/tests/setup.ts) so individual tests don't need to call `expect.extend` themselves.

### Scoping or silencing rules

Disable a single rule for a known false positive:

```tsx
expect(
  await axe(container, { rules: { "color-contrast": { enabled: false } } }),
).toHaveNoViolations();
```

Run against a subtree instead of the whole rendered DOM by passing a more specific element instead of `container`. Disable as narrowly as possible — never blanket-disable a rule globally; that hides regressions.

### Layer overlap

axe-core is the same engine Lighthouse uses internally for its accessibility category — rule overlap with the Lighthouse layer is intentional. The component layer catches regressions before they reach a built page; Lighthouse catches the integration-level shape (heading order, landmarks, document-wide contrast). Both layers staying green is the contract.
